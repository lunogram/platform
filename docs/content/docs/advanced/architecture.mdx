# Architecture

Lunogram is built as a modern, distributed system designed for reliability, scalability, and extensibility. This page provides an overview of the key architectural components and how they work together.

## Core Components

### Single Binary Architecture

Lunogram compiles to a single Go binary that contains:

- **HTTP Server** - RESTful API for the web console and client SDKs
- **Event Consumers** - Background workers processing events from NATS
- **Cluster Node** - Participates in distributed coordination
- **Provider Runtime** - WASM execution environment for plugins

This simplifies deployment significantly - there's no need to manage separate API servers, workers, or schedulers.

### Database Layer (PostgreSQL)

Lunogram uses PostgreSQL with three logical databases for separation of concerns:

| Database | Purpose |
|----------|---------|
| `management` | Organizations, admins, projects, campaigns, journeys, providers |
| `users` | User profiles, events, subscriptions (per-project data) |
| `journey` | Journey state, user progress, scheduled steps |

This separation allows for:
- Independent scaling of user data
- Easier data isolation for multi-tenant deployments
- Optimized indexes for different query patterns

### Event Streaming (NATS JetStream)

All asynchronous operations flow through NATS JetStream:

<Mermaid chart={`
sequenceDiagram
  participant User
  participant API
  participant NATS as NATS Stream
  participant Consumer
  participant Processing

  User->>API: Action
  API->>NATS: Publish
  NATS->>Consumer: Deliver
  Consumer->>Processing: Process
`} />

**Key streams:**

| Stream | Purpose |
|--------|---------|
| `events` | User events from client SDKs |
| `campaigns` | Campaign send requests |
| `journeys` | Journey state transitions |
| `lists` | List membership updates |

**Benefits:**
- **Durability** - Messages persist until acknowledged
- **Replay** - Reprocess events if needed
- **Backpressure** - Consumers process at their own pace
- **Scalability** - Add more consumers for higher throughput

### Caching & Coordination (Redis)

Redis serves multiple purposes:

- **Distributed Locks** - Ensure only one node processes a job
- **Leader Election** - Coordinate which node runs scheduled tasks
- **Cluster State** - Track active nodes and their health
- **Caching** - Fast access to frequently-read data

### WASM Provider System

Providers (email, SMS, push) are implemented as WebAssembly modules:

<Mermaid chart={`
graph TD
  core["Lunogram Core"] <--> runtime["WASM Runtime\n(Extism)"]
  runtime --> resend["Resend\nPlugin"]
  runtime --> twilio["Twilio\nPlugin"]
  runtime --> custom["Custom\nPlugin"]
`} />

**Why WASM?**

- **Security** - Plugins run in a sandbox with limited capabilities
- **Language Agnostic** - Write plugins in Go, Rust, or any WASM-compatible language
- **Hot Reload** - Update providers without restarting the application
- **Isolation** - Plugin crashes don't affect the core system

**Plugin Interface:**

Every provider implements two functions:
- `manifest()` - Returns metadata and configuration schema
- `send()` - Sends a message through the provider

## Distributed Architecture

### Cluster Coordination

When running multiple Lunogram nodes, they coordinate through Redis:

<Mermaid chart={`
graph TD
  node1["Node 1"] <--> redis["Redis"]
  redis <--> node2["Node 2"]

  redis --- election["Leader\nElection"]

  node1 --> tasks["Scheduled Tasks\n(Journey scheduling, list updates)"]
  redis --> tasks
  node2 --> tasks
`} />

**Leader Election:**
- Uses Redis distributed locks (Redlock algorithm)
- Only the leader runs scheduled tasks
- Leadership automatically transfers on failure
- Heartbeats ensure liveness detection

**Node Registration:**
- Each node registers with a unique ID
- Heartbeats maintain registration
- Stale nodes are automatically cleaned up

### Scaling

Lunogram scales horizontally by adding more nodes:

| Component | Scaling Strategy |
|-----------|------------------|
| HTTP API | Load balance across nodes |
| Event Processing | Add consumers, partition streams |
| Database | Read replicas, connection pooling |
| Redis | Redis Cluster for large deployments |
| NATS | NATS clustering for HA |

## Security Model

### Authentication

- **JWT Tokens** - Stateless authentication for API requests
- **API Keys** - Public (client) and secret (admin) keys per project
- **SSO** - SAML and OpenID Connect for enterprise deployments

### Authorization

- **Organization** - Top-level tenant isolation
- **Project** - Data isolation within organization
- **Role-Based** - Owner, admin, member permissions

### Data Isolation

- Per-project user databases
- API keys scoped to projects
- WASM sandbox for provider plugins

## Monitoring

Lunogram integrates with standard observability tools:

- **OpenTelemetry** - Distributed tracing
- **Prometheus Metrics** - Cluster health, message throughput
- **Structured Logging** - JSON logs with correlation IDs
