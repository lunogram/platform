Users represent your customers, the people who receive your messages. Each user profile stores contact information, preferences, and custom properties that you define. This data powers personalization in campaigns, segmentation in lists, and branching logic in journeys.

<Callout type="info">
  **Users vs Admins**: Users are your customers who receive messages. Admins are
  team members who log into Lunogram to create campaigns and manage the
  platform. They're completely separate.
</Callout>

---

## User Profiles

Every user has a profile containing:

- **Identifiers**: How Lunogram recognizes the user
- **Contact info**: Email, phone number for messaging
- **Preferences**: Timezone, locale, subscription states
- **Custom data**: Any properties you define

### Identifiers

| Field          | Description                                            |
| -------------- | ------------------------------------------------------ |
| `anonymous_id` | Identifier for unknown visitors                        |
| `external_id`  | Your system's unique identifier (user ID, customer ID) |

Users need at least one identifier. The `anonymous_id` tracks users before they sign up or log in. Once you know who the user is, call `user.upsert` with their `external_id` to link their anonymous activity to their known identity.

**Where anonymous IDs come from:**

- **Auto-generated**: The [JavaScript SDK](/sdks/javascript) creates one automatically when using the browser client
- **From analytics tools**: Pass an existing ID from PostHog, Segment, or Mixpanel
- **Your own system**: Use any unique string you generate

```typescript title="JavaScript SDK"
// The browser client auto-generates an anonymous ID,
// but you can override it with one from another tool
client.user.upsert({
  anonymousId: posthog.get_distinct_id(),
  data: { source: "marketing_site" },
});

// Later, link to a known user
client.user.upsert({
  anonymousId: posthog.get_distinct_id(),
  externalId: "user_123",
  email: "alice@example.com",
});
```

### Contact Information

| Field   | Format                       | Required For    |
| ------- | ---------------------------- | --------------- |
| `email` | `user@example.com`           | Email campaigns |
| `phone` | E.164 format (`+1234567890`) | SMS campaigns   |

### Preferences

| Field      | Description                              | Example                |
| ---------- | ---------------------------------------- | ---------------------- |
| `timezone` | IANA timezone for send-time optimization | `America/New_York`     |
| `locale`   | Language/region for template selection   | `en`, `es-MX`, `fr-CA` |

## Custom Data

Store any data you need on user profiles. Custom properties let you personalize messages, segment users into lists, and make decisions in journeys.

### Setting Custom Data

<Tabs items={['JavaScript SDK', 'API']}>
  <Tab value="JavaScript SDK">
    ```typescript
    client.user.upsert({
      externalId: "user_123",
      email: "alice@example.com",
      data: {
        first_name: "Alice",
        plan: "premium",
        company: "Acme Inc",
        signup_source: "webinar",
        lifetime_value: 2500,
        preferences: {
          theme: "dark",
          notifications: true
        }
      }
    })
    ```
  </Tab>
  <Tab value="API">
    ```bash
    curl -X POST https://your-instance.com/api/client/users \
      -H "Authorization: Bearer pk_..." \
      -H "Content-Type: application/json" \
      -d '{
        "external_id": "user_123",
        "email": "alice@example.com",
        "data": {
          "first_name": "Alice",
          "plan": "premium",
          "company": "Acme Inc",
          "signup_source": "webinar",
          "lifetime_value": 2500
        }
      }'
    ```
  </Tab>
</Tabs>

### Using Custom Data

Once stored, custom data is available everywhere via `user.data`:

**In campaigns** (personalization):

```handlebars
Hi
{{user.data.first_name}}, Thanks for being a
{{user.data.plan}}
member! {% if user.data.company %} We hope the team at
{{user.data.company}}
is enjoying Lunogram. {% endif %}
```

**In lists** (segmentation):

```
user.data.plan = "premium"
AND
user.data.lifetime_value > 1000
```

**In journeys** (branching):

```
Gate: user.data.plan = "enterprise"
  Yes → Send enterprise onboarding
  No → Send standard onboarding
```

### Nested Properties

Store structured data using nested objects:

```typescript title="JavaScript SDK"
client.user.upsert({
  externalId: "user_123",
  data: {
    address: {
      city: "Austin",
      state: "TX",
      country: "US",
    },
    preferences: {
      email_frequency: "weekly",
      product_updates: true,
    },
  },
});
```

Access nested properties with dot notation:

```handlebars
{{user.data.address.city}}, {{user.data.address.state}}
```

### Common Custom Properties

| Property                         | Type          | Use Case                   |
| -------------------------------- | ------------- | -------------------------- |
| `first_name`, `last_name`        | string        | Personalization            |
| `plan`, `tier`                   | string        | Feature-based segmentation |
| `company`, `team_size`           | string/number | B2B targeting              |
| `signup_source`, `referrer`      | string        | Attribution tracking       |
| `lifetime_value`, `orders_count` | number        | Value-based segmentation   |
| `last_login`, `last_purchase`    | date          | Engagement tracking        |
| `tags`, `interests`              | array         | Multi-value segmentation   |

## Updating User Data

User properties merge on update. New properties are added, existing properties are overwritten, and unmentioned properties remain unchanged.

<Callout type="warn">
Updates use a **shallow merge**. Top-level keys in `data` are replaced entirely. If you have a nested object like `address: { city: "Austin", state: "TX" }` and update with `address: { city: "Dallas" }`, the result will be `address: { city: "Dallas" }` — the `state` key is lost. To preserve nested fields, include the full object in your update.
</Callout>

**Initial upsert:**

```typescript title="JavaScript SDK"
client.user.upsert({
  externalId: "user_123",
  data: { plan: "free", city: "Austin" },
});
// Result: { plan: "free", city: "Austin" }
```

**Later update:**

```typescript title="JavaScript SDK"
client.user.upsert({
  externalId: "user_123",
  data: { plan: "premium", company: "Acme" },
});
// Result: { plan: "premium", city: "Austin", company: "Acme" }
```

### Updating from Journeys

Use the [Update step](/journeys/types#update) to modify user data based on journey context. The template is a JSON string with Liquid expressions that can reference `user` properties and upstream step data via `journey.<data_key>`:

```json
{
  "full_name": "{{ user.data.first_name }} {{ user.data.last_name }}",
  "last_score": "{{ journey.score_lookup.body.score }}"
}
```

In this example, `score_lookup` is the data key of an upstream [Action step](/journeys/actions) whose response contained a `score` field.

## Creating Users

| Method             | When to Use                                            |
| ------------------ | ------------------------------------------------------ |
| **JavaScript SDK** | Track users from your website or web app               |
| **Client API**     | Create users from your backend                         |
| **CSV Import**     | Bulk import users directly                             |
| **List Import**    | Import users and add them to a static list in one step |

### CSV Import

Upload a CSV file from the Users page to bulk create or update users. Each row becomes a user profile.

```csv
external_id,email,first_name,last_name,plan,company
user_001,alice@example.com,Alice,Smith,premium,Acme Inc
user_002,bob@example.com,Bob,Jones,free,Globex
user_003,carol@example.com,Carol,White,premium,Initech
```

The `external_id` column is required. The following columns map to standard user fields:

`email`, `phone`, `first_name`, `last_name`, `timezone`, `locale`

All other columns (like `plan` and `company` above) become custom properties.

<Callout type="info">
  Importing via a [static list](/lists#static-lists) also creates users, but
  adds them to the list. Direct CSV imports only create or update profiles.
</Callout>

## Subscriptions

Users can subscribe or unsubscribe from each [subscription group](/settings/subscriptions). Subscription state controls whether a user receives messages for that group.

| State            | Behavior                                                                        |
| ---------------- | ------------------------------------------------------------------------------- |
| **Subscribed**   | User receives messages                                                          |
| **Unsubscribed** | User has opted out and will not receive messages                                |
| **Not set**      | Depends on your project settings (default subscribe or require explicit opt-in) |

### Why Use Multiple Subscription Groups?

Instead of a single "subscribed/unsubscribed" toggle, you can create separate groups for different message types:

| Group               | Example Messages                               |
| ------------------- | ---------------------------------------------- |
| **Marketing**       | Promotions, sales, new product announcements   |
| **Product Updates** | Feature releases, changelog, tips              |
| **Transactional**   | Order confirmations, password resets, receipts |
| **Weekly Digest**   | Summary emails, newsletters                    |

This lets users opt out of promotional emails while still receiving important product updates or transactional messages.

### How Users Manage Subscriptions

- **Preference center**: Include `{{ preferences_url }}` in emails to link to a page where users manage all their subscription groups
- **One-click unsubscribe**: Include `{{ unsubscribe_url }}` for a direct unsubscribe link for that specific group
- **SMS reply**: Users can reply STOP to unsubscribe from SMS messages
- **Your app**: Call the SDK or API to update subscription state from your own UI

<Callout type="warn">
  Never send messages to unsubscribed users. Lunogram automatically filters them
  out, but respecting user preferences is essential for deliverability and legal
  compliance.
</Callout>
